# Custom fork vs upstream Strata on two RTX 5080s (UD-Q4_K_XL)

I run Qwen3.8-Flash-Next UD-Q4_K_XL with Strata on Linux with two 16 GB RTX 5080s. I had been using eddoursul's custom fork, ported to Linux, and wanted to see how upstream v0.1.38 compares on the same machine and, if there is a gap, where it comes from. This started from [a post on r/LocalLLM](https://www.reddit.com/r/LocalLLM/comments/1wu6fka/qwen_38_flash_next_doubled_strata_throughput_on/).

On this machine and this workload the custom fork was faster in both prefill and decode. The largest changes in these tests came from helper-GPU prompt processing and adaptive expert residency. Numbers and limits below.

Machine: Ryzen 9 9900X, 185 GiB RAM, two RTX 5080 16 GB (driver 595.58.03, CUDA 13.0), Rocky Linux 10.1. GPU 0 links at PCIe 5.0 x8, GPU 1 at x4. The driver reports no peer access between the cards in either direction.

Custom is eddoursul/custom [`25e86c7`](https://github.com/eddoursul/Strata/commit/25e86c762b569f8d4a5f434e3cb31b4b916ee50d) plus my Linux changes on [`linux-2x5080`](https://github.com/kim-haneol/Strata/tree/linux-2x5080). Upstream is v0.1.38 [`99f3dbd`](https://github.com/Niko1221/Strata/commit/99f3dbd0b21d1401b3769e0c0d963913607f380b), built from source with `STRATA_MMQ_KQUANTS=ON` (off in the stock build), so it uses the Q4_K prompt MMQ kernels. Apart from the diagnostic options below, upstream's inference source is unchanged. Upstream was run in two modes: layer split with `--layer-split 25` (what `auto` picked in the API run below), and the host peer tier with `--peer-device 1 --peer-prefill-rows 0`.

| Mode | GPU 1 (main) | GPU 0 |
| --- | --- | --- |
| custom | all layers, K/V | expert tier; also computes its experts during prompt processing |
| upstream layer split | layers 0-24 | layers 25-47, drafter |
| upstream host peer | all layers, K/V, all prompt processing | expert tier through pinned host buffers |

## How it was measured

The engines don't generate the same text, so decode tok/s from free generation compares different outputs. I added an opt-in `--spec-follow` mode to both engines instead. The engine is given a saved 300-token continuation, emits it in place of its own argmax, and accepts drafts that match it. It also counts how many emitted tokens differ from its own argmax. The continuation is an earlier custom-fork answer to a short coding prompt.

Each condition runs in a fresh engine process that gets five requests, all emitting the same 300 tokens:

- the same 54-token code prompt three times in a row (I report the median),
- a copy request: the prompt contains the 300-token answer and asks for it back verbatim,
- a 32,768-token input made of a synthetic prefix and the code prompt.

Shared settings: 64K context, INT8 K/V, 8K prompt chunk, MTP with 4-token windows, 10 CPU workers, no prompt-cache reuse, expert-cache adaptation every round. Cache budgets are similar, but expert placement, counts and execution differ between the modes by design. Experts cached at start (main + second GPU): custom 2460 + 4109, layer split 2554 + 2566, host peer 2432 + 4096. Per-request numbers are in [`results.json`](https://github.com/kim-haneol/Strata/blob/q4-diagnostics/docs/causal-diag/results.json).

| Mode | 32K prefill | Code decode (median) | Copy decode | Decode after 32K |
| --- | ---: | ---: | ---: | ---: |
| custom | 2773.0 | 110.6 | 73.6 | 104.1 |
| upstream layer split | 2015.7 | 78.1 | 61.3 | 69.1 |
| upstream host peer | 1522.2 | 70.3 | 54.2 | 72.0 |

All numbers are tok/s. Custom is 37.6% ahead of layer split in 32K prefill and 41.7% ahead in code decode.

## Where the difference comes from

I changed one setting at a time from a reference run. Each result is relative to that reference only. Don't add the percentages up.

**Prompt processing on the second GPU.** With `--no-prompt-offload`, custom's 32K prefill dropped from 2730.5 to 1365.6 tok/s. The 2730.5 is the average of two reference runs in separate processes (2736.3 and 2724.8).

**Prompt chunk size.** Raising custom's chunk from 8K to 16K moved 32K prefill from 2730.5 to 3724.1 tok/s (+36.4%). This table holds the chunk at 8K for all three modes. In a separate API run, both upstream modes were asked for 16K and dropped to 8K on their own to fit their expert caches. Custom kept 16K on the same cards.

**Adaptive expert residency.** Without adaptation, the decode gap is much smaller:

| Mode | Code decode, static cache | Code decode, adaptive |
| --- | ---: | ---: |
| custom | 55.3 | 110.6 |
| upstream layer split | 43.9 | 78.1 |
| upstream host peer | 44.8 | 70.3 |

The static values average two reference runs. Adaptation helps all three modes, and helps custom the most.

In custom, `--adapt-every` turns on both cache moves and predictor learning. I added a flag to separate them and ran a second set of custom runs:

| Custom, second set | Code | Copy | Decode after 32K |
| --- | ---: | ---: | ---: |
| reference | 53.1 | 42.0 | 56.5 |
| reference, repeated | 56.9 | 44.4 | 56.2 |
| learning only | 57.5 | 45.4 | 56.9 |
| adaptation only | 106.5 | 72.0 | 103.4 |
| adaptation + learning, helper prefetch off | 99.4 | 70.5 | 92.5 |
| expert count capped at 2460 + 2660 | 53.1 | 42.4 | 49.9 |

Adaptation alone gets almost all of the speedup. Learning alone is 4.4% above the midpoint of the two references (55.0). The two references themselves are about 7% apart, so that is not a gain I can claim. The full adaptation-plus-learning run (110.6) is from the first set, so I'm not attributing the 110.6 vs 99.4 difference to prefetch alone. These runs are in [`phase2-results.json`](https://github.com/kim-haneol/Strata/blob/q4-diagnostics/docs/causal-diag/phase2-results.json).

The capped run starts custom with 5120 experts, the same total layer split had in its runs. Code decode stayed at 53.1. Decode after the 32K prompt fell 11.4% and prefill fell 4.6%. The same expert count still means different bytes, placement and kernels, so this isn't a like-for-like kernel comparison.

**MTP.** MTP is active in upstream too, so it doesn't explain the gap by being on or off. With decode speculation disabled (one token per window; MTP memory and MTP prompt work kept) against the static-cache references:

| Mode | One-token windows | MTP windows |
| --- | ---: | ---: |
| custom | 33.9 | 55.3 |
| upstream host peer | 28.6 | 44.8 |
| upstream layer split | 29.6 | 43.9 |

All three emitted about 3.4 tokens per verify window on the code prompt, and drafting took 1.9-2.2 ms per window. The bigger per-window differences were in verification and host/CPU-pool time. The engine's timer categories overlap, so they don't add up to a breakdown.

**Prompt lookup** went both ways. In custom it lowered code decode from 55.3 to 44.7 tok/s and raised the copy request, whose answer is already in the prompt, from 41.7 to 56.7. Upstream's code-prompt changes were within run-to-run spread; its copy request gained more.

## The API run

Before the diagnostic runs I measured both upstream modes through the normal API with free generation (three 300-token code requests, 32K retrieval):

| | Layer split | Host peer | Custom, 2026-09-30 |
| --- | ---: | ---: | ---: |
| 32K retrieval prefill | 2068.9 | 1504.4 | 3616.7 |
| Code decode, median of 3 | 79.5 | 76.0 | 108.3 |

The custom column is from a run three days earlier, with a 16K chunk and different generated text. It is a reference point, not a matched comparison, and the tables above don't use it. Upstream's free-generation code decode (79.5 / 76.0) is close to its forced-continuation numbers (78.1 / 70.3). Configs and results are in [`docs/local-ab`](https://github.com/kim-haneol/Strata/tree/q4-diagnostics/docs/local-ab).

## Limits

- The forced continuation is a throughput tool. It says nothing about code accuracy or output quality.
- The continuation came from custom, which may favor custom's drafts. Same tokens don't mean the same expert routing or arithmetic across engines.
- The three code requests run in one process, one after another. Only the reference conditions were repeated in fresh processes. There are no confidence intervals.
- Unrelated OpenROAD jobs were running on the CPU (about 218-800% aggregate process CPU in the intervals I checked). That makes small differences hard to attribute.
- The results are for this machine, this model and these prompts. The PCIe links are unequal and there is no P2P; other boards may behave differently.

33 engine processes, 133 requests: 5 ordinary-generation checks with diagnostics off, which matched the original builds token for token, and 128 forced-continuation requests. Every process exited 0.

## Linux and two-5080 changes in the custom fork

The expert tier, its prompt offload and adaptive residency are eddoursul's work. I didn't change how they operate. To run the fork on this machine I changed ([`linux-2x5080`](https://github.com/kim-haneol/Strata/tree/linux-2x5080)):

- GCC build fixes, including an unsequenced `off[j1++]` read in the prompt expert batching.
- The Linux CPU pool treated each logical CPU as a core. It now groups SMT siblings from sysfs. The prompt path's PLE reader thread also restores the process CPU mask instead of inheriting the host loop's pin.
- The server added `--layer-split auto` to any config listing two GPUs. This engine has no such flag and exits, so it is skipped when `--second-gpu` is set.
- The QSA top-k host check counted two reserved rows and stopped a 262,144-token arena at startup. With the fix the full arena starts and served requests up to 32K; I haven't tested inputs near 262K.
- GPU roles. My first config used physical GPU 0 (x8) as the main card and GPU 1 (x4) as the expert tier. Swapping them, so the expert tier is on the x8 link, raised 4K prefill from 972.2 to 1539.7 tok/s (+58%) and 32K prefill from 2703.7 to 3614.3 (+34%) at 64K context with the same binary. That is one API run per order, and the first run also had `--stats` on ([data](https://github.com/kim-haneol/Strata/blob/linux-2x5080/docs/gpu-order-20260930.json)). It was by far the largest effect among the config changes I measured.
- The rest of the config: 1024 MiB reserve on each card, 8 MiB helper prefetch and 0.20 PCIe share from a fixed-text sweep.
- The opt-in diagnostic flags used above. All are off by default.

## Data

- [`linux-2x5080`](https://github.com/kim-haneol/Strata/tree/linux-2x5080): custom engine source. It matches the source of the second-set diagnostic build; the first-set build lacked the two second-set flags (16 lines of `generate.cpp`). I haven't rebuilt the re-committed branch.
- [`q4-diagnostics`](https://github.com/kim-haneol/Strata/tree/q4-diagnostics) (this branch): upstream diagnostic patch, `tools/causal-diag` (harness), `tools/local-ab` (API run).
- [`docs/causal-diag`](https://github.com/kim-haneol/Strata/tree/q4-diagnostics/docs/causal-diag): run plans, input/binary hashes, fixtures, and full results for both sets.
- [`docs/local-ab`](https://github.com/kim-haneol/Strata/tree/q4-diagnostics/docs/local-ab): API run configs and results.

Raw logs and telemetry aren't published because they include unrelated processes on the machine. The manifests hold SHA-256 hashes of the binaries, fixtures, MTP files and other selected inputs; the four GGUF shards are listed by size only. The scripts are the ones I ran locally. They depend on my worktrees, unpublished run directories and build outputs, so running them elsewhere needs those paths and files set up first.
